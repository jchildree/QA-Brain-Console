# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is **not** a software project with a build/test/lint pipeline -- there is no `package.json`, no compiler config, and no test runner anywhere in the tree. It is an **Obsidian vault** ("QA Second Brain") used as a personal quality-management thinking layer, plus a couple of standalone prototype artifacts and portable Claude skill templates. Do not go looking for build commands; none exist.

Because there is no git repository initialized at the root (`Is a git repository: false`), do not assume version control is in place -- check with the user before suggesting `git init` or relying on git history for context.

## Repository layout

- **`qa-brain/`** -- the actual Obsidian vault content. This is the real thing being maintained.
  - `SOP/`, `INCIDENT/`, `CAP/`, `CHANGE/`, `AUDIT/`, `TRAINING/`, `MEETING/` -- record folders, one per document type. Each is currently just a `.gitkeep` placeholder plus whatever real records get created over time.
  - `Notes/` -- free-form drafting/note-taking, exempt from the status lifecycle and controlled vocabulary below. See the ID convention and controlled-vocabulary notes further down for how it differs from the seven record types.
  - `_templates/` -- Templater templates (`SOP.md`, `CAP.md`, `INCIDENT.md`, `CHANGE.md`, `AUDIT.md`, `TRAINING.md`, `MEETING.md`) that define the frontmatter schema and section structure for each record type. When asked to draft a new SOP/CAP/Incident/etc., follow the shape of the matching template in this folder exactly (frontmatter fields, section numbering, revision history table).
  - `_dashboards/` -- Dataview query boards (`Home.md`, `CAP-Tracker.md`, `SOP-Control.md`, `Audit-Prep.md`, `Incident-Trends.md`) plus an Obsidian canvas board. These contain live Dataview queries (`TABLE ... FROM "docs/qa-brain/<Folder>" WHERE ...`) -- note the queries reference a `docs/qa-brain/...` path prefix, not the bare folder names used elsewhere, so check the actual vault mount point before editing queries.
  - `_meta/` -- vault documentation: `README.md` (architecture/folder map/ID conventions), `Plugin-Stack.md` (required Obsidian plugins + IQ/OQ/PQ validation checklist), `Automation-Setup.md` (QuickAdd workflow configs, Obsidian Git setup, Templater/Metadata Menu settings).

- **Document ID convention**: `{TYPE}-{YYYYMMDD}-{seq}`, e.g. `SOP-20260528-001`, `INC-20260528-001`, `CAP-20260528-001`, `CHG-20260528-001`, `AUD-20260528-001`, `TRN-20260528-001`, `MTG-20260528-001`, `NOTE-20260528-001`. IDs are auto-generated by Templater from the template frontmatter -- preserve this pattern if creating records manually.

- **Status lifecycle** for records: `Draft -> In Review -> Approved -> Obsolete`. Legal values only -- don't invent synonyms. Notes are exempt from this lifecycle entirely -- they have no `status` field.

- **Relationship model**: `SOP <-- INCIDENT --> CAP`, with `AUDIT` and `TRAINING` feeding into `INCIDENT`/root-cause analysis. Records cross-link via `related_documents` / `related_records` frontmatter fields and `[[wikilinks]]`, not by folder nesting.

- **This vault is a personal drafting/analysis layer, not the system of record.** The real QMS system is "Intellect" (EQMS) -- approved records get pushed there; this vault is where drafting, root-cause analysis, and audit-prep happen first. Don't treat anything here as final/authoritative documentation of the live QMS.

- **`QA-Brain-Project/`** -- a nested copy of parts of the vault (`Welcome.md`, the same three `.tsx` files as the root). Treat it as a duplicate/staging copy, not a separate concern -- if asked to edit vault content, confirm which copy the user means.

- **`*.tsx` files at the repo root** (`eqms_cognitive_compiler_dashboard.tsx`, `eqms_engine_registry_sandbox.tsx`, `gemini_multimodal_workspace_compiler.tsx`) -- standalone, self-contained single-file React prototypes (Claude-generated artifacts), each 900-1700 lines. They are **not wired into any build system** in this repo (no `package.json`, no bundler config) and are not imported by anything else here. Treat edits to these as edits to a standalone demo file, not part of a larger app -- don't assume shared components, routing, or state exist outside the file itself.

- **`skills/`** -- portable Claude Code skill templates written for *other* projects, not for this repo:
  - `eqms-adr-skill/` -- an Architectural Decision Record skill template intended for a separate "EQMS microservice" codebase (FastAPI + React + SQL Server stack referenced in its examples). It is not applicable to this vault's own content.
  - `phase-status skill/` -- a generic "Phase Status" governance skill template (canonical phase registry, fixed status lexicon `DORMANT/UNBLOCKED/ACTIVE/FOCUS/COMPLETE/SUPERSEDED`, ADR-gated transitions) meant to be installed per-project at `/docs/skills/phase-status-skill/SKILL.md`. It is a template to hand to other projects, not a skill currently bound to this repository.
  - When asked to "install" or "apply" one of these skills, that means copying/adapting it into a *different* target project the user is working on -- ask which project if it isn't clear from context.

## Working conventions specific to this vault

- When drafting new QA records (SOPs, CAPs, incidents, etc.), match the existing template's frontmatter fields and section structure precisely -- Dataview dashboards query on those exact frontmatter keys (`status`, `owner`, `root_cause`, `effectiveness_status`, `department`, `review_date`, etc.), and typos silently break queries.
- Controlled vocabulary for `status`: `Draft, In Review, Approved, Obsolete`. For `type`: `SOP, CAP, INCIDENT, CHANGE, AUDIT, TRAINING, MEETING`. For `department`: `QC, QA, IT, Operations`. For `effectiveness_status`: `Pending, Pass, Fail, N/A`. Notes (`type: NOTE`) are not part of this controlled vocabulary -- they have no `status`, `department`, or `effectiveness_status` fields; only `title`, `folder`, `tags`, and `related_documents`.
- Version control here (if/when set up) is meant to double as the audit trail (every save = a commit, per Obsidian Git), so avoid rewriting history or force-pushing on this vault even if git is later initialized.

## Frontend routing & pages (`app/frontend/`)

`app/frontend/src/App.tsx` routes 29 of the 31 page components in `app/frontend/src/pages/`. Two pages are intentionally unrouted:

- **LoginPage** and **SetupPasswordPage** are rendered directly by `app/frontend/src/components/AuthGate.tsx`, not via `<Route>`. AuthGate sits above `<Routes>` inside `<BrowserRouter>` and switches on session/auth state (`LoginPage` when unauthed) or on `location.pathname === '/setup'` (`SetupPasswordPage`, checked before the authed/unauthed branch so a new user can always reach it). `/setup` therefore works as a URL but does not appear in App.tsx's `<Routes>` list -- that's by design, not an omission.
- Every record type (SOP, CAP, INCIDENT, CHANGE, AUDIT, TRAINING, MEETING, NOTES) has a complete Dashboard/Editor/Intake triple with type-prefixed names (`SopDashboard`/`SopEditor`/`SopIntake`, etc. -- no generic `Dashboard.tsx`/`Intake.tsx` files remain). Each Editor route uses a thin `*EditorRoute` wrapper that reads `:filename` from `useParams` and returns `null` if it's absent, so the editor component itself never renders without a filename.
- Literal routes (`/sop/new`) are declared before their parameterized sibling (`/sop/:filename`) for each record type, though React Router matches by specificity regardless of declaration order.
