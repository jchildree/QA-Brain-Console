# EQMS Engine Registry Sandbox

Source: `raw/eqms_engine_registry_sandbox.tsx` (1452 lines). Standalone React/Tailwind prototype, no build system, no backend, dark slate/teal/indigo theme.

Despite the filename, this is a 5-tab lab EQMS console demo (Dashboard, Document Control, CAP & Deviations, Employee Training, Schema Registry Admin) -- not a generic "engine registry." All data is in-memory mock arrays, no persistence. Core idea is "schema-as-data": JSON blueprint objects define dynamic form fields, interpreted at render time to build CAP intake forms; an admin tab lets a user add fields at runtime with auto-versioning. Includes threshold-based auto-escalation to a simulated outbox, a double-key e-signature modal (hardcoded PIN "1234", fake crypto hash), an append-only audit log, and a training quiz + mock file-upload competency flow. No actual charting despite "trend charts" copy -- all analytics are static counts or raw JSON dumps.

## Feature map (see [[Dashboard Feature Gap Map]] for cross-file synthesis)

Applicable: schema-as-data blueprint pattern (echoes the vault's own Templater-schema-per-type model, strongest architectural idea across all 3 files), status-lifecycle pill cards (Draft/Approved/Effective maps directly to `status` field), append-only audit log panel (maps to "Obsidian Git = audit trail" convention in CLAUDE.md), training quiz/competency tracking (maps to TRAINING record type).

Not applicable: all chemistry/lab domain content (ICP-MS, water turbidity, IACUC), MSSQL/NVARCHAR(MAX) JSON backend + generated SQL scripts, transactional-outbox bridge to a "parent LIMS" (no analogous integration exists), fake PIN+hash e-signature (security theater, not implementable as-is), mock file-upload with setTimeout-simulated verification, multi-tenant session context (vault is single-user).
